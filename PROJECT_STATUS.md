- **W34 — Leave Balance Engine (Ledger) — Complete.** New `leave_balance_entries` table — append-only and immutable by construction: no route or service function ever `UPDATE`s or `DELETE`s a posted row; a mistake is corrected with a compensating `reversal` entry. Seven entry types per the frozen enum (`opening_balance`, `accrual`, `carry_forward`, `usage`, `reversal`, `expiry`, `manual_adjustment`); this workstream's API only ever posts `manual_adjustment` — accrual/carry-forward/expiry postings and the automatic `usage` posting on approval are explicitly reserved for W35/a later accrual scheduler, not built here. A displayed balance is never a stored column — `getEmployeeBalances` always reconstructs it live as `SUM(amount)` grouped by leave type. `leavePolicyId` is resolved server-side by the single internal `postLedgerEntry` primitive, never client-supplied: for a request-related posting it's taken from the leave request's own already-resolved policy (so a later policy change can never reinterpret history, per the frozen plan's Historical Consistency rule); otherwise it's freshly resolved via W33's `resolveApplicablePolicy`, reused unchanged. Integrity is enforced by two partial unique indexes rather than application-level locking alone: `(relatedLeaveRequestId, entryType)` prevents duplicate usage postings and double reversals for the same request; `(organizationId, employeeId, leaveTypeId, entryType, sourceReference)` prevents duplicate opening balances and duplicate accrual for the same employee/policy/period — a caller supplies a stable `sourceReference` idempotency key (e.g. `"accrual:2027-01"`) for postings meant to be safely retried. A unique-constraint violation under concurrent/retried posting is caught and translated into `DuplicateLedgerEntryError` (new `isUniqueViolation`-based translation, same `dbErrors.ts` precedent already used elsewhere) rather than silently double-posting. Amount sign direction is validated in the service layer (opening_balance/accrual/carry_forward must be positive, usage/expiry must be negative, reversal/manual_adjustment may be either but never zero) — not a schema constraint, since Postgres `CHECK` can't vary by another column's enum value without a trigger, and the frozen plan didn't call for one. A manual adjustment requires a non-empty `reason` (enforced in both the OpenAPI schema and the service layer) and is always audit-logged (`leave_balance.manual_adjustment`) — routine ledger postings are not, since they're self-documenting through the ledger's own reason/actor/timestamp columns (Architecture Principle 6).
