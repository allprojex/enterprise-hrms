- **W24 — Skills & Qualifications — Complete.** ADR-010's "skill", "qualification_type", and "certification_type" Master Data domains (W7) — the plan groups Certifications into this workstream since no other frozen workstream owns that domain. Three new org-scoped tables (`employee_skills`, `employee_qualifications`, `employee_certifications`, all `employeeId` cascading, same shape as `employee_documents`/W23) + a new `lib/employeeSkillsQualifications.ts` service with full list/add/update/remove per entity. New dedicated route file `routes/employeeSkillsQualifications.ts` (mirrors the branches/departments/positions one-file-per-resource pattern rather than growing the already-large `employees.ts` further), mounted in `routes/index.ts`. 12 endpoints total (`GET/POST` + `PATCH/DELETE .../:id` for each of skills/qualifications/certifications under `.../employees/:employeeId/...`), gated by the existing `employee.read`/`employee.write` — no new permission. Each `*_code` field is free text from its Master Data domain, unvalidated against the domain's item list, same precedent as `employeeDocuments.categoryCode`. Audit-logged (`employee_skill.added/updated/removed`, same pattern for qualification/certification). Employee detail page gains three list cards (Skills/Qualifications/Certifications) with a category picker + one descriptor field for quick-add, and remove; the backend's `PATCH` (full field edit) is not yet exposed as an edit-in-place UI — quick-add/remove covers the common case, matching Known Issue #7's precedent of a built-but-not-fully-UI-verified capability. Migration `0013_noisy_kulan_gath.sql` (three new tables, purely additive) generated with a hand-authored `.down.sql`, not applied.
- **W25 — Transfers — Complete.** Department/branch/position reassignment, distinct from W12's `restructure` endpoints (which move a department/position itself, not an employee). New `transferEmployee` in `lib/employees.ts` (alongside `separateEmployee`/`rehireEmployee`, not a new file — a single action on the core employee record, same as those): reuses `assertEmployeeReferencesValid` for cross-org reference validation (Architecture Decision 3, ADR-012) rather than duplicating it, rejects a no-op transfer (`EmployeeTransferNoChangeError` when department/branch/position would all stay the same), updates the employee's current placement, then calls W22's `recordEmploymentPeriodEvent` (`eventType: "transfer"`) to preserve the dated before/after history in `employment_periods` — the row on `employees` always reflects only the *current* placement, never the history. New `POST .../employees/:employeeId/transfer` (`employee.write`, no new permission), returns the updated Employee. No schema change — reuses `employees`' existing department/branch/position columns and W22's `employment_periods` table, so no migration. Employee detail page gains a Transfer dialog (department/branch/position selects, defaulting to "keep current", + effective date) next to Separate.
- **W26 — Promotions — Complete.** Position/title change with an effective date, recorded via W22 — no compensation/salary field or concept exists anywhere in this schema, and none was introduced (out of scope per the frozen plan). New `promoteEmployee` in `lib/employees.ts`, alongside `transferEmployee`/`separateEmployee`/`rehireEmployee` (not a new file, same single-action-on-the-core-record precedent). Unlike Transfer, only touches `positionId` — Promotion is specifically a position change, not department/branch. Reuses `assertEmployeeReferencesValid` for cross-org validation (same as Transfer, not duplicated) and rejects a no-op promotion (`EmployeePromotionNoChangeError` when the target position is already the employee's current one). Calls W22's `recordEmploymentPeriodEvent` (`eventType: "promotion"`) to preserve dated history in `employment_periods` without overwriting it — `employees.positionId` still holds only the *current* position. New `POST .../employees/:employeeId/promote` (`employee.write`, no new permission), returns the updated Employee. No schema change — reuses `employees.positionId` and W22's `employment_periods` table, so no migration. Employee detail page gains a Promote dialog (position select + effective date) next to Transfer.

## Known Issues

1. No Module Management *enforcement* — the registry (W3), per-org enablement (W4), and both the backend (W5) and frontend (W6) gate mechanisms now exist, but no route or page composes either gate yet, since no module has a shipped feature to gate. Everything still ships unconditionally on for every org.
2. ~~Organization switcher is non-functional...~~ **Resolved by W1.** `GET /auth/me` now resolves and returns `activeOrganizationId` server-side (session's switched org → legacy `user.organizationId` → any other active membership → null), and every org-scoped page/query and the dashboard summary use it instead of the legacy field. The sidebar switcher is a working dropdown over `/me/organizations`.
3. ~~No user registration/creation UI anywhere...~~ **Resolved by W10.** Admins can now invite an email that has no account yet via the Admin console (or the API directly); the invitee accepts via a public link, sets their own name and password, then logs in normally. 4. ~~Organization Settings is a raw JSON blob, not structured configuration.~~ **Resolved by W2.** Replaced by the Organization Configuration Engine: `organization_settings` now stores one validated, versioned row per (organization, namespace) instead of one uncontrolled blob per organization. `general` and `terminology` namespaces are implemented now; further namespaces (module enablement, numbering formats, branding, ...) register into the same engine as their owning workstream lands. Existing data preserved automatically via a column default, no migration script needed.
5. ~~Roles and permissions are fixed seed data — no admin path to define org-specific ones.~~ **Resolved by W11.** System role templates stay fixed and protected; an org copies one into its own row and customizes that copy's permissions.
6. ~~Core Reports not started.~~ **Resolved by W17.** Headcount, Workforce Status, and Audit Summary now run tenant-scoped from the Admin console's Reports tab, with CSV export.
7. Profile picture upload not yet verified live in the browser.
8. ~~No "already linked" indicator on an employee record — re-linking just fails with a 409.~~ **Resolved by W14.**
9. ~~Dashboard's `ACTIVE_MODULE_COUNT` is a hardcoded constant, not derived from a real module registry.~~ **Resolved by W18.** Now a real per-organization count from the module registry + enablement overrides.
