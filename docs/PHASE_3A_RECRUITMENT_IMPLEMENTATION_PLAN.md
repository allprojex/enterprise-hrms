## 1. Executive Product Scope

A configurable, enterprise-grade Recruitment & Hiring module spanning the full lifecycle: recruitment configuration → job requisition → approval → vacancy publishing (internal and/or public) → candidate application → screening/scoring → pipeline movement → interviews → offers → pre-employment checks → conversion to employee — with talent pools, notes/tags, background/reference checks, and reporting throughout. It must serve businesses, churches, NGOs, schools, hospitals, hotels, and government bodies (the existing `org_type` enum) without hardcoding any single organization type's terminology or workflow, exactly per CLAUDE.md's Core Principles.

## 2. Design Principles

1. **One shared foundation, no exceptions.** No "church recruitment" or "school recruitment" code path. A ministry/volunteer role, a teaching vacancy, and a corporate role are the same `job_requisitions`/`vacancies`/`applications` rows differentiated by configuration (employment type, workplace type, free-text Master Data codes), never by branching logic.
2. **Configuration before custom code.** Pipeline stages, rejection/withdrawal reasons, candidate sources, screening templates, and offer rules are all organization-configurable data, not enum-coded assumptions.
3. **Reuse before invention.** Recruitment is the *second* HR-operations module built on this platform (after Leave/Attendance/ESS in Phase 2B) — every architecture decision below defaults to reusing an existing mechanism (Module Gating, Master Data, the five-tier permission model, the append-only ledger/history pattern, `assertBelongsToOrganization`, `employee_user_links`, `fileStorage`/`documentValidation`, `recordAuditEvent`, the Organization Configuration Engine) rather than building a parallel one. Where a genuinely new mechanism is needed (candidate accounts, public routes, pipeline-stage history), it is scoped as narrowly as the equivalent existing pattern.
4. **Tenant isolation is non-negotiable — including for candidates.** A candidate record belongs to exactly one organization (see §3.4, Open Decision). No cross-organization candidate visibility, matching, or deduplication of any kind.
5. **Public surfaces are the highest-risk surfaces.** Every public (unauthenticated) endpoint is designed assuming a hostile internet: rate-limited, minimally informative on failure, never leaking another organization's existence or data, and never trusting a client-supplied identifier for anything but a lookup key.
6. **History is append-only where it matters.** Pipeline-stage movement, interview scorecards once submitted, and offer versions are never overwritten in place — the same principle W22 (`employment_periods`) and W34 (`leave_balance_entries`) already established.
7. **No payroll dependency.** Salary/compensation fields on requisitions and offers are simple, recruitment-scoped numeric ranges — never a foreign key into a compensation/grade system that doesn't exist in this schema.
8. **Money-shaped decisions get flagged, not guessed.** Every genuine open product decision is listed in §17 with a recommended default that lets implementation proceed unblocked, plus the alternative and trade-off — never silently resolved.

## 3. Domain Model

### 3.1 Configuration layer
- **Recruitment Settings** — one validated row per organization (org-level toggles and defaults; see §9 for the full field list). Given the number of structured, relational fields (default workflow reference, stage lists, approval rules), this is **not** a good fit for the generic Organization Configuration Engine's JSON-namespace pattern (W2/W38's precedent) — it is a dedicated table, mirroring the reasoning `leave_policies` used over Master Data (ADR-010's "dedicated schemas where a domain doesn't fit the generic shape").
- **Recruitment Workflows** — named, org-scoped pipelines (e.g., "Standard Hiring," "Volunteer Onboarding," "Teaching Staff"). An organization may define more than one; each requisition/vacancy is created against exactly one workflow.
- **Recruitment Stages** — ordered stages belonging to a workflow (e.g., Applied → Screening → Interview → Offer → Hired), each with a category (see §4.2) and required/optional flag.
- **Reference data** (rejection reasons, withdrawal reasons, candidate sources, employment types, workplace types) — reuses the existing Master Data engine (W7/ADR-010) as new domains, exactly like `separation_reason`/`document_category` already work. `employment_type` and `gender` already exist as shared enums on `employees` and are reused as-is, not redefined.

### 3.2 Requisition → Vacancy → Application chain
- **Job Requisition** — the internal request to hire, carrying headcount, budget, justification, and approval state. One requisition may produce **one or more** vacancies (default expectation is 1:1; splitting one approved headcount into multiple location-specific postings is supported, not mandated — see §17).
- **Vacancy** — the postable unit: internal-only, external-only, or both; carries its own lifecycle independent of the requisition's (a requisition can be "approved" while its vacancy is still "draft").
- **Application** — one candidate's submission against one vacancy. A candidate may hold multiple applications (to the same or different vacancies), each with its own independent pipeline state.

### 3.3 Candidate identity
- **Candidate** — the person/profile record, organization-scoped (§3.4).
- **Candidate Account** — an optional, separate authentication identity (email + password or magic-link), decoupled from the profile exactly the way `employee_user_links` decouples an employee record from a login (W14's precedent: "this row's presence/absence is metadata only — it never grants or implies access on its own"). A candidate can exist with zero applications-in-progress accounts (anonymous, email-tracked) or with an account (returning-candidate convenience).
- **Internal candidate** — an existing employee applying to an internal vacancy. Reuses `employee_user_links`/`resolveOwnEmployeeId` (W14/W33's precedent) to resolve "which employee is this candidate" — never a second identity system for internal applicants.

### 3.4 Open Decision — global vs. tenant-scoped candidate identity
**Recommended default: tenant-scoped.** A candidate record (and its account, if any) belongs to exactly one organization. The same real person applying to two different organizations on this platform creates two independent candidate rows with no linkage — deduplication/matching is by normalized email **within** an organization only, never across organizations.
**Alternative:** a single global candidate identity shared across every tenant (one login, one profile, applications fan out to multiple orgs).
**Trade-off:** the global model is more convenient for a candidate and is how large multi-tenant job boards work, but it directly conflicts with CLAUDE.md's "never expose another organization's data" principle — even metadata like "this email has applied elsewhere on this platform" is a cross-tenant disclosure. The tenant-scoped model costs candidates re-entering their profile per organization; that cost is accepted deliberately.
**Blocking?** No — tenant-scoped is the safe, immediately-implementable default.

## 4. Status/State Models

### 4.1 Requisition status
`draft → pending_approval → approved → (open | partially_filled | filled) → closed`, with `rejected` and `cancelled` as terminal exits from `pending_approval`/`approved`. `filled_count` increments as linked applications convert to employees (§13); a requisition auto-transitions to `filled` when `filled_count == requested_headcount`, and to `closed` only via an explicit action (a requisition can be closed with headcount unfilled — e.g., a role is scrapped).

### 4.2 Vacancy status
`draft → pending_approval (if the org requires vacancy-level approval, otherwise skipped) → scheduled → published → paused ⇄ published → closed → archived`, plus `cancelled` as a terminal exit from any pre-`closed` state. `scheduled` exists specifically to support a future `publish_at` timestamp without a background scheduler (see §17) — a vacancy in `scheduled` is not publicly visible until an operator manually flips it, or a future scheduler workstream automates the flip.

### 4.3 Stage categories (not stage names)
Every org-defined stage belongs to exactly one fixed **category**, so system logic (e.g., "is this candidate hired," "does this stage allow rejection") never depends on an organization's own stage *label*:
`applied | screening | interview | assessment | offer | hired | rejected | withdrawn`.
An organization can rename, reorder, add, or remove stages freely within a workflow, but every stage must map to one of these categories. `hired` and `rejected`/`withdrawn` are terminal categories — no further movement is possible from them except an explicit, permissioned "reopen" action (§7).

### 4.4 Application status
Derived from the candidate's current stage's category, not a separately-tracked field — avoids the two ever disagreeing. `application_stage_history` (§9) is the only place stage transitions are recorded; the application row always points at its *current* stage only.

### 4.5 Interview status
`scheduled → completed | cancelled | no_show`, with `rescheduled` handled as cancelling the old row and creating a new one (immutable history, same as the Foundation's "never edit history in place" pattern) rather than mutating a scheduled interview's date in place.

### 4.6 Offer status
`draft → pending_approval → approved → issued → (accepted | declined | expired | withdrawn) `, with `superseded` applied to a prior version when a new offer version is issued for the same application (§14).

### 4.7 Background/reference check status
`requested → in_progress → (completed | flagged | unable_to_complete)`.

## 5. Security Model

- **Every authenticated recruitment route** composes `requireMembership` + `requireModuleEnabled("recruitment")` + a `recruitment.*` permission check, exactly the pattern every Phase 2B route already uses (`requireAuth → requireMembership → requireModuleEnabled → requirePermission`).
- **Every organization-scoped query independently re-verifies ownership** of every referenced record (candidate, requisition, vacancy, application) via `assertBelongsToOrganization`/an equivalent scoped lookup — a route-level permission check is never treated as sufficient proof that a body-supplied ID belongs to the caller's organization (Architecture Principle 5, reused verbatim from Phase 2B).
- **No client-supplied identity ever substitutes for a resolved one.** A candidate's own applications are resolved via their candidate-session identity, never a client-supplied `candidateId`; an internal applicant's employee is resolved via `resolveOwnEmployeeId`, never a client-supplied `employeeId` — the exact discipline W33/W39 already established.
- **File uploads** (CVs, supporting documents, background-check attachments) reuse `lib/documentValidation.ts`'s real file-signature sniffing (never trusting `Content-Type` alone) and `lib/fileStorage.ts`'s org-scoped directory convention, with a new `"recruitment"` subdirectory family. Size/type limits mirror W23's existing 10MB/PDF-JPEG-PNG-DOCX-XLSX policy unless a genuine reason to diverge is found at implementation time.
- **Malware scanning** is a documented integration boundary (§15), not built in this phase — uploads are validated by signature/size/type only, same posture as every existing upload path in this codebase today.

## 6. Public Careers Security Model

Public careers routes are **new territory** for this codebase — every other public route to date (`/invitations/:token`, `/reset-password/:token`) is token-gated and single-purpose. Careers introduces genuinely open, crawlable, form-submitting public surfaces. Design:

- **Public job listing/detail** (`GET /careers/:orgSlug`, `GET /careers/:orgSlug/jobs/:publicId`) — read-only, only `published` vacancies with `externalVisible = true`, scoped by the organization's own slug (already unique per `organizations.slug`) so one org's careers page can never enumerate another's postings. Returns only public-safe fields (title, description, location, employment/workplace type, salary range if the vacancy marks it visible) — never internal fields (hiring manager, requisition linkage, internal notes).
- **Public identifiers.** Vacancies and applications get a separate `publicId` (a short random token, not the serial primary key) for every public-facing URL and status-check reference — the internal integer PK is never exposed to an unauthenticated client, closing off ID-enumeration entirely (a `publicId` is looked up, never counted from).
- **Application submission** (`POST /careers/:orgSlug/jobs/:publicId/apply`) — the highest-risk endpoint:
  - Rate-limited per IP via `express-rate-limit` (already a dependency, same library `/auth/login`'s `loginRateLimiter` uses), with a stricter window than login given the larger payload (file uploads).
  - A honeypot field plus a documented CAPTCHA integration boundary (§15) — ships with the honeypot + rate limit; real CAPTCHA (hCaptcha/reCAPTCHA) is a vendor choice deferred to an integration workstream, not blocking.
  - File uploads pass through the same `documentValidation.ts` signature/size/type checks as every other upload in this codebase.
  - Duplicate-submission handling: a second submission from the same normalized email to the same vacancy within a short window (e.g., a double-click) is treated as idempotent (returns the existing application, does not create a second row); an org-configured **reapplication waiting period** (§9) applies to a genuinely new attempt after a prior rejection/withdrawal on the *same* vacancy.
  - Never leaks whether a given email has applied before, in error responses or timing — mirrors `forgot-password`'s existing "always return the same confirmation" discipline (ADR-017's precedent).
- **Candidate identity/verification.** Where a candidate account is used (org-configurable — §17), email verification follows the existing invitation/reset-password pattern: a generated token, a public preview endpoint, a public consume endpoint, short TTL, never emailed in plaintext without a real provider (reuses the Resend `EmailProvider` abstraction, W19).
- **Secure application-status access.** For an anonymous (no-account) applicant, status is checked via the same email-verified-link pattern (a signed, time-limited token emailed at submission), never a bare "enter your email to see your status" lookup, which would let anyone probe arbitrary emails.
- **Signed/private document access.** A candidate's own uploaded documents are never served from a guessable static URL — reuses `fileStorage.ts`'s existing org-scoped-storage-key indirection (the same pattern that already prevents a profile picture or employee document from being directly URL-guessable).
- **PII, consent, and privacy notice versioning** are first-class fields on the candidate record (§9's `candidate_consents`), not an afterthought — every public application capture records which privacy-notice version was shown and consented to, at submission time, immutably.
- **Cross-tenant disclosure prevention.** No public endpoint ever accepts or returns an organization ID directly — only the organization's own `slug`, and every downstream query is scoped by the organization resolved from that slug, never a client-supplied numeric ID (mirrors `organizations.slug`'s existing uniqueness and the platform's general "never trust a client-supplied ID as authorization" rule).

## 7. Permission Matrix

Following the five-tier model Phase 2B established (own / manager-scoped / HR org-wide / approval authority / policy administration), extended with a **recruiter-assigned** tier specific to this module (a recruiter is "assigned" to a requisition/vacancy the same way a manager is derived from `reportingManagerId` — via an explicit `recruiterId`/`hiringManagerId` column, not a role name):

| Area | Permission key(s) | Own | Assigned (recruiter/hiring manager) | Org-wide (HR) |
|---|---|---|---|---|
| Recruitment settings | `recruitment_settings.read` / `.manage` | — | — | ✔ manage |
| Requisitions | `requisition.read` / `.create` / `.update` / `.cancel` | ✔ read own-created | ✔ (hiring manager on their own requisition) | ✔ |
| Requisition approval | `requisition.approve` | — | ✔ where explicitly delegated | ✔ |
| Vacancies | `vacancy.read` / `.manage` / `.publish` / `.close` | — | ✔ (assigned recruiter) | ✔ |
| Candidates | `candidate.read` / `.manage` | — | ✔ (candidates in their pipelines) | ✔ |
| Candidate sensitive data | `candidate.sensitive.read` | — | — | ✔ (narrower than `candidate.read`, mirrors `employee.notes.read`'s precedent) |
| Applications | `application.read` / `.manage` | ✔ (candidate's own, via candidate session — separate authorization path, §7.1) | ✔ | ✔ |
| Pipeline movement | `application.pipeline.move` | — | ✔ | ✔ |
| Candidate notes | `candidate.notes.read` / `.write` | — | ✔ | ✔ |
| Candidate documents | `candidate.documents.read` / `.manage` | ✔ (candidate's own) | ✔ | ✔ |
| Interviews | `interview.read` / `.manage` | — | ✔ (own scheduled interviews as interviewer) | ✔ |
| Scorecards | `scorecard.submit` / `.read_all` / `.finalize` | — | ✔ submit own | ✔ read_all, finalize |
| Offers | `offer.read` / `.manage` / `.approve` / `.issue` / `.withdraw` | — | ✔ manage draft | ✔ approve/issue/withdraw |
| Background checks | `background_check.read` / `.manage` | — | — | ✔ |
| Talent pools | `talent_pool.read` / `.manage` | — | — | ✔ |
| Recruitment reports | `recruitment.reports.read` | — | ✔ (own workload/pipeline scope) | ✔ |
| Employee conversion | `candidate.convert_to_employee` | — | — | ✔ (mirrors `employee.write`'s existing gate) |

Notes:
- **Reused, not reinvented:** the final conversion step (§13) reuses the existing `employee.write` permission on the actual `POST .../employees` creation path — `candidate.convert_to_employee` gates the recruitment-side trigger only, not a second employee-creation authority.
- **Scorecard integrity:** `scorecard.submit` never implies `scorecard.read_all` — an interviewer must not see colleagues' scores before submitting their own (bias prevention), the same "coarse gate + fine-grained check" pattern `employee.notes.read` established.
- **Avoiding permission explosion:** no separate permission per pipeline stage category, per vacancy visibility type, or per document type — a stage move, a note, and a document all reuse the *one* corresponding area's permission plus the assigned/org-wide tier check, not N stage-specific permissions.
- **§7.1 Candidate-session authorization** is a *separate* authorization path from membership-based permissions entirely — a candidate authenticates (if using an account) or verifies (if anonymous, via emailed token) into a **candidate session**, distinct from an `organization_memberships` row, and can only ever act on their own candidate/application rows, resolved server-side the same way `resolveOwnEmployeeId` resolves an employee — never a client-supplied `candidateId` or `applicationId` without ownership re-verification.

## 8. Module-Gating Strategy

- The `recruitment` module already exists in the registry (W3, seeded `status: "hidden"`) — Phase 3A's foundation workstream does **not** need to create it, only (a) confirm/extend its `requiredModuleKeys` (none expected — recruitment does not depend on Leave/Attendance/ESS) and (b) flip its registry `status` to `"active"` once the module is genuinely usable (mirrors the precedent that `leave`/`attendance`/`employee_self_service` were flipped, or intentionally left `"hidden"`, per their own workstream's judgment in Phase 2B — `status: "hidden"` only affects catalog visibility, never per-org enablement, so this is a low-stakes, reversible flag).
- Every authenticated internal route composes `requireModuleEnabled("recruitment")`, identical to every Phase 2B route.
- Every internal frontend route wraps in `<ModuleGate moduleKey="recruitment">`, identical to Phase 2B's pages.
- **Public careers routes are never module-gated by `requireModuleEnabled` in the request-authorization sense** (there is no membership to check) — instead, the public listing/detail/apply routes independently check `recruitment_settings.enabled` (an organization-level toggle, distinct from the platform Module Registry's per-org `organization_modules.enabled`, though the two should be kept in sync operationally) and return a generic "careers page not available" response, never a 500 or a leak of internal state, exactly mirroring how a disabled module degrades gracefully elsewhere in this codebase.
- **ESS's internal-vacancies/My Applications section** (§16) checks `recruitment` module accessibility independently within the ESS page, the same pattern W39 already established for its My Leave tab against the `leave` module — ESS itself stays gated only by `employee_self_service`, and a disabled `recruitment` module degrades that one section to a controlled message, not a broken page.

## 12. Screening, Scoring, and Pipeline Notes

Knockout questions (`vacancy_questions.isKnockout`) are evaluated server-side at submission time against `expectedAnswer` where the question type supports it (yes/no, multiple-choice); a failed knockout does **not** silently reject the application — it flags `application_answers.knockoutFailed` for recruiter review, since automatic rejection on a possibly-miskeyed expected answer is a real-world failure mode worth a human check (open to reconsideration at implementation time, not blocking). `applications.score` is a computed, non-authoritative rollup (mirrors `leave_balance_entries`' "never a stored source of truth" principle) recomputed from `application_scores` on read, not trusted as stored state for authorization decisions.

## 13. Employee Conversion

`convert-to-employee` is a single transactional service function (mirrors W35's approve-and-post-ledger-entry transaction shape): validates the application is in a `hired`-category stage and every non-waived `pre_employment_requirements` row is `satisfied`, then calls the **existing** `createEmployee` path (same service `POST /organizations/:id/employees` already uses — reused, not duplicated) inside the same transaction, then inserts the `candidate_employee_links` provenance row. Duplicate-conversion is prevented by `candidate_employee_links`'s `(applicationId)` unique constraint (a second attempt sees a unique-violation, translated to a typed `AlreadyConvertedError`, mirroring `DuplicateLedgerEntryError`'s precedent) — genuinely idempotent under retry. An internal candidate (already an employee) converting via a *new* internal application does not create a second employee record — the conversion path checks `candidates.linkedInternalEmployeeId` first and, if set, records provenance against the existing employee rather than calling `createEmployee` again. Failure at any point rolls back the whole transaction — no employee is ever created without its provenance link, and no provenance link exists without a real employee.

## 14. Offers — Versioning and Approval

An `offers` row is a stable envelope; `offer_versions` holds the actual content, one immutable row per revision. Editing a `draft` version updates that row in place; editing an `approved`/`issued` version creates a **new** version row and marks the prior one `superseded` — never overwritten, so "what was actually offered and when" is always reconstructable, the same discipline `interview_scorecards` and `application_stage_history` use. `offers.currentVersionId` always points at the latest non-superseded version. Whether multiple *active* (non-superseded, non-terminal) offers may exist per application simultaneously is an org policy flag (§9, §17) — default is **one active offer per application**, enforced by the partial unique index noted in §9's table.

## 16. Data Retention and Privacy

- `candidate_consents` captures the privacy-notice version and consent text at the moment of application — immutable, never reinterpreted.
- `recruitment_settings.candidateDataRetentionMonths` (org-configurable, default recommendation: 24 months post-final-decision — see §17, flagged for legal review) drives a **manual, permissioned purge action** in this phase, not an automated background job — this codebase has no scheduled-job infrastructure yet (Foundation's own Known Issue #1 precedent notes "no scheduled jobs" as an explicit gap), so automated retention enforcement is an integration boundary (§15's implicit addition — a future scheduler workstream), while the *configurable period* and a *manual "purge candidates older than X" admin action* both ship now.
- A candidate data-subject deletion request is handled by a genuine hard-delete path for `candidates` (unlike employees, which are never hard-deleted per ADR-013) — cascading through `candidate_documents`/`candidate_notes`/`applications`/etc., **except** where a `candidate_employee_links` row exists (a converted candidate's recruitment history becomes part of the employee's permanent record and is retained under the employee-record retention rules instead, not deleted).
- **This is a compliance-adjacent area requiring professional legal review** (see §17 — explicitly flagged, not resolved by this document): exact retention periods, lawful basis for processing, and cross-border data handling for Ghanaian and other-jurisdiction organizations are legal questions this document does not and cannot resolve.
